# 派子代理什么时候省钱：opus 父代理 × 主会话上下文 × 派 / 不派

>
> **更正（2026-10-05，同日）**：初版把所有缓存写都按 1.25× 输入价计。transcript 的 `usage.cache_creation` 显示**主会话
> 全部是 1 小时缓存**（`ephemeral_1h_input_tokens`，2× 输入价），**子代理全部是 5 分钟缓存**（1.25×）。主会话缓存写因此
> 被低估。按正确口径重算后结论方向不变——两档上下文下派活都更贵、每次约多 $0.21——但绝对值上升、百分比下降：
> 小上下文 +63% → **+54%**，大上下文 +19% → **+15%**。下文数字均为更正后口径。

## 结论

**在这组任务上，无论主会话上下文是小（约 2.5 万 token）还是大（约 12 万 token），派子代理都比主代理自己做更贵**——
小上下文贵 54%，大上下文贵 15%，绝对差额都是约 $0.21（恰为两个子代理的花费）。H1「派活省不省钱主要看主会话
上下文大小」**未被支持**：真正的决定量是**每个 task 能让主会话少跑多少轮**，而这组小 task 一轮都没省下来。

## 方法

- textkit 两个 task（与真实测试、build-task-dispatch 验收相同的种子），spec-guard 0.44.0 约定块，**不派**组不带
  `--dispatch`、**派**组带 `--dispatch`，其余完全相同。
- `claude -p --model opus --setting-sources project,local`，三插件经 `--plugin-dir` 加载（agent-skills 0.6.11、
  spec-guard 0.44.0、tier-guard 0.2.4），`/build auto` → `--continue` `approve`。
- **大上下文**：`--append-system-prompt-file` 给主会话加约 10 万 token 的仓库资料，每次运行开头加随机串，避免跨运行
  共享缓存。开跑前验证：主会话首条上下文 118,437 token，**子代理 20,441 token——子代理不继承**。
- 每种条件 2 次，共 8 次；整体账 = 主会话 + 全部子代理 transcript，按 `message.id` 去重、按每条消息的模型单价折算
  （Opus 5.5 $4/$20、缓存读 $0.20；Sonnet 5.5 $2/$10、缓存读 $0.20；缓存写按 `usage.cache_creation` 区分：5 分钟 1.25×、
  1 小时 2× 输入价——主会话是 1 小时，子代理是 5 分钟）。
- 8 次全部：测试通过、4 个提交、父代理 `claude-opus-5-5`、子代理 `claude-sonnet-5-5`。

## 为什么没省下来

**派活时主会话的轮次没有减少。** 不派组主会话 11–16 条消息，派组也是 11–16 条；大上下文下两组的主会话缓存读都在
140 万–210 万 token。textkit 的每个 task 主代理自己做只要 2–3 次工具调用（写测试、写实现、跑测试）；派出去之后，
主代理要调用 Agent、读 diff、跑测试、提交、勾选——轮次相当。主会话一侧零节省，子代理的花费（每个约 $0.10）全是增量。

## 回本条件（推算，待更大 task 验证）

每少一轮主会话，大约省下「主会话上下文 × opus 缓存读价」：12 万 token 时约 $0.024，26 万（用户日常均值）时约 $0.05。
一个 sonnet 子代理约 $0.10（5 分钟缓存写，计价未受更正影响）。因此一个 task 至少要让主会话**少跑约 4–5 轮（12 万上下文）或 2 轮（26 万上下文）**才回本。
小而明确的 task 少不了这么多轮，**永远不划算**；需要大量探索、调试、反复修改的 task 才可能划算——本实验没有覆盖。

## 局限

- 只测了两个很小的 task；更大 task 的回本点是推算，未实测。
- 大上下文用追加系统提示模拟长会话；计费机制相同（每轮重读），但真实长会话的上下文是对话历史。
- `大 · 派 #2` 在 Task 1 提交前因 spec 未定义非 ASCII 处理停下问人，补答一轮后完成；它的成本因此多一轮问答。
- 每种条件 2 次，方差可见（同条件内差 $0.01–0.21），结论方向一致。

## 对规则的含义

- spec-guard 的「不派」条件应以 **task 的工作量**为主：规格明确、预计几次工具调用就能完成的 task 由主代理自己做；
  主会话上下文大只是放宽门槛的因素，不是充分条件。
- tier-guard `tier-routing` 的「自己做」提示同理：所选模型不比主会话便宜时不派（必要条件），task 很小也不派。
