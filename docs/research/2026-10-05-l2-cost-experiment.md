# L2 对照实验：Sonnet 5.5 vs Opus 5.5

> 状态：**已完成**　｜　日期：2026-10-05　｜　总花费：$4.35
>
> 结论：**在典型 L2 任务上 Sonnet 5.5 严格占优——质量相同（10/10 对 10/10），每任务成本约为 Opus 5.5 的 56%。** 现行候选目录把 L2 路由到 `sonnet` 是对的，不需要改。

## 为什么要做

外部公开数据给出的每任务总花费是 **Opus 5.5 $5.98、Sonnet 5.5 $7.60**——Opus 又强又便宜。如果这对本工作负载成立，候选目录的 L2 档（`implementation + bounded_change → sonnet`）就是一个又贵又弱的选择，`cost_rank` 也排错了。

本仓此前**没有一条成本数据**（审计日志 3461 条记录，无任何 token 字段）。临时聚合本机 182 份子代理 transcript 得到的每模型均值方向与外部数据一致，但那**不是对照实验**：各模型接到的是不同的任务，测出来的是「派给各档的活有多重」，不是「同一个活上哪个模型更省」。spec 要求结论来自受控对照，所以有了这次实验。

## 设计

| 要素 | 做法 |
|---|---|
| 任务 | 10 个 L2 任务：单文件、规格明确、有自动验收（解析时长、LRU、semver 规范化、RLE、区间合并、CSV 行解析、罗马数字、令牌桶、字典差异、INI 解析） |
| 夹具自检 | 先用参考实现跑全部测试，**10/10 通过**——确保子代理失败只能是子代理的问题，不是测试的错 |
| 两档 | 每个任务分别派 `model: sonnet` 与 `model: opus`，**提示词逐字相同**，仅工作目录不同 |
| effort | 两档都在各自默认值，均为 `medium`（宿主 catalog 的 `thinking_by_model`）。这正是 tier-guard 的真实处境——它给 Claude 子代理设不了 effort |
| 质量评分 | 用**原始测试副本**在隔离目录里重跑，不用子代理工作目录里那份（防止它改测试让自己通过）；同时核对测试文件的 SHA-256 是否被改 |
| 成本 | 从子代理 transcript 逐条读 `usage` 累加：输入、缓存写（1.25× 基础输入价，5 分钟 TTL）、缓存读（Sonnet 5.5 $0.20/MTok、Opus 5.5 $0.20/MTok）、输出。单价取自 claude-api 文档 |
| 账目核对 | 20 条派活的 agentId → 任务/档位映射，逐条从 transcript 核对实际模型与工作目录，**20/20 一致**；不靠调用顺序推断 |
| 执行 | 先 1 任务 × 2 档试点量出单价，再分 3 批并发跑完其余 9 × 2 |

实际执行模型：`claude-sonnet-5-5` × 10、`claude-opus-5-5` × 10（会话模型已切到 Opus 5.5，`opus` 别名随之解析到 5.5）。

## 为什么方向和外部数据相反

**成本几乎全是固定开销。** 20 次派活输出合计只有 1,337 token（每次 56–79），而缓存写合计 919,658 token。每次派活都要先写入子代理的基础上下文（系统提示 + 工具定义，约 30K–66K token），这部分与任务做了什么无关，只按模型单价计费。所以对短任务：

> **每任务成本 ≈ 固定上下文 × 模型单价。** Opus 单价是 Sonnet 的两倍，成本就接近两倍，几乎与任务难度无关。

外部数据测的是长任务。那里 token 量主导、单价不主导，Opus 可能因为轮次少、走弯路少反而更省。**「哪个更省」取决于任务长度，不是模型的固有属性。** 外部数据本身没错，只是它回答的不是 L2 的问题。

## 两个需要知道的混杂因素

**缓存预热。** 试点与第 1 批的缓存写约 66K token，第 2、3 批降到约 30K——基础上下文被缓存后，后续派活改为读取。绝对成本因此在后两批降了约 35%。同一批里两档面对相同的缓存条件，**逐对比较的倍数不受影响**。

唯一例外是 **07-roman 的 Opus**：缓存写 54,561 token（没吃到缓存），成本 $0.340，倍数 2.79×。**这个离群值是缓存未命中造成的，不是模型属性。** 去掉它，倍数范围是 1.36–2.04×。

**会话模型。** 实验前把会话模型从 Opus 5 切到了 Opus 5.5。切换前 `opus` 别名解析到 `claude-opus-5`，切换后解析到 `claude-opus-5-5`——同一个别名、同一个会话、只改了一个设置。这次实验 Opus 侧 10/10 都是 5.5。

## 局限

**① 天花板效应——最重要的一条。** 两档都 10/10，意味着这组任务**区分不出质量**。实验证明的是「Sonnet 足以胜任典型 L2 任务」，**不是**「Sonnet 永远不需要升到 Opus」。若存在更难、Sonnet 会失败的 L2 任务，这次测不出来。

不过 L2 的定义本身就是「有明确验收、范围在单模块内」，这组任务是该定义的典型代表；真正难的、需要取舍的属于 L3，那里本就路由到 Opus。

**② 每格只跑一次**，方差未知。

**③ 结论不外推到其他 effort。** 两档都在默认 `medium`。

**④ 只覆盖 Claude 侧。** Codex 侧 L2 是 `gpt-6.1-sol / medium`，没有参与这次对照。

## 对 tier-guard 的影响

- **候选目录不改。** L2 → `sonnet` 是对的。
- **`cost_rank` 补上定义**（见 spec「Model catalog」）：它按 token 单价排序，不是每任务成本保证。本实验证实在 L2 上两者一致，但长任务上可能反转。
- **成本数据从此能自动积累**：`SubagentStop` 已开始记录宿主回报的 token 用量（`d4ba144`），`/tier-report` 按实际执行模型列出平均 token。这次是手工聚合 transcript，下次可以直接从审计日志取。
