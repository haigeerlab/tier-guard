# 与 spec-guard 联调：派活整体账（ledgerlite 模块，Claude × Codex）

> 状态：**完成（含补跑 S / W 组）**　｜　日期：2026-10-05 至 10-06　｜　Task 27　｜
> 运行与成本报告：spec-guard 会话（module-cost-report）；核对：tier-guard 会话（本文）

## 设计（spec-guard 会话设计，tier-guard 评审后定稿）

- **种子项目 ledgerlite**：约 15 个文件、1500 行纯 Python 记账库，带 unittest，种子全绿；预埋两处种子测试不覆盖的缺陷
  （parser 读成浮点导致月报差 1 分；timeutil 按本地时区切月）。spec 补全了边界约定。
- **5 个 task + Checkpoint**：1、2 小而明确；3 修跨文件 1 分钱差额（描述只写现象）；4 给 Entry 加必填字段（改 5 个文件）；
  5 只给一个失败验收用例、需调试定位。Task 5 另有不公开的隐藏用例。
- **组别**（三组只在约定块上不同，提示词逐字相同）：**N** 不开 `--dispatch`；**R**「默认不派」规则；**F**「每个 task 都派」
  （spec-guard 0.44.0 规则段）；**G** 同 F 但 L3 定义补上「取舍」二字。
- **运行**：交错串行；Claude `claude -p --model opus --setting-sources project,local`，三插件 `--plugin-dir` 显式加载，
  隔离用户级配置；Codex `codex exec`，主代理固定 `gpt-6.1-sol/medium`；每次单独 `TIER_GUARD_LOG_DIR`；中途停下用同一句
  预设回答续跑。价格按 tier-guard 口径（缓存写 5 分钟 1.25×、1 小时 2× 输入价）。
- **分工**：spec-guard 会话出每次运行的成本报告与评分；tier-guard 会话从 transcript / 线程表 / tier-guard 日志独立核对
  派活次数、档位、请求模型、实际执行模型与子代理用量。

| F2 | 26 | 5（Task 4 为 L3→opus） | $1.106 | $1.863 | $2.969（F 均值 $2.81，**+39%**） |
| G1 | 23 | 5（全部 L2→sonnet） | $0.985 | $1.030 | $2.015 |

- **Task 4 是唯一派了更便宜的 task**：G 组 Task 4 均值 $0.54，N 组 $0.70，**便宜 23%**；主会话轮次 G 为 2 / 3，N 为 8 / 4。
  这正是回本条件：派出去让主会话少跑的轮次，省下的钱多于 sonnet 子代理的花费。

结束记录的用量普遍少最后一条 assistant 消息（它在 SubagentStop 之后才落盘，多轮子代理同样如此），结束时记录的用量只是下限。

## 结果：Codex（主代理 gpt-6.1-sol/medium，子代理 gpt-6-luna/high）

| 运行 | 主会话轮次 | 派活 | 主代理 | 子代理 | 合计 |
|---|---|---|---|---|---|
| N1 / N2 | 24 / 23 | 0 | $0.688 / $0.726 | — | 均值 **$0.71** |
| R1 / R2 | 31 / 27 | 0 | $0.760 / $0.708 | — | 均值 $0.73 |
| F1 | 70 | 5（全部 luna/high） | $1.520 | $0.069 | $1.589 |
| F2 | 79 | 5（全部 luna/high） | $1.703 | $0.078 | $1.781（F 均值 $1.69，**+138%**） |

- **Luna 子代理很便宜**（5 个合计 $0.07），但 **F 组主会话轮次翻了约 3 倍**：主线程调用 `wait_agent` 25 / 31 次，
  `timeout_ms` 只取 10000 或 30000，即每 10–30 秒轮询一次；每次返回都是一轮主会话，按 sol 单价重读整段上下文。
  `exec` 也从 N 组的 22–23 次涨到 36–37 次（主代理复核子代理产出）。
- **Codex 自带审查线程**：每次运行目录下还有 `codex-auto-review/low` 线程（`source={"subagent":{"other":"guardian"}}`，
  不是主代理派的），N、R 组也有；各次 153k–411k token，未定价，成本报告单列，不计入派活。
- R 组两次都一个没派。

**tier-guard 核对**：F1、F2 子线程按 `parent_thread_id` 挂到主线程，各 5 个、全部 `gpt-6-luna/high`；tier-guard Codex 日志
各 5 条 `codex-spawn`；子代理合计（缓存按 10% 计）独立计算 $0.0686 / $0.0780，与报告一致；若缓存按全价则为 $0.37 / $0.46，
仍远小于主代理花费。Codex hook 只拿到 `opaque_token`，tier-guard 日志里没有档位，档位只能看派活 prompt 与成本报告。

## 结论

1. **派活能省钱，但只对极少数 task 成立**：要求派出去能让主会话少跑很多轮（Task 4：8→2 轮），且子代理模型比主会话便宜。
   小 task、探索量不够的 task 派了都更贵。这与 [派活成本实验](2026-10-05-dispatch-cost-experiment.md) 的回本条件一致，
   并给出了第一个正面实测。
2. **「默认不派」方向对，但门槛过高**：R 组 4 次运行一次没派，连 Task 4 也没选中。spec-guard 已把门槛改为「只派预计改动
   3 个以上文件、验收明确的 task」，补跑 S 组验证。
3. **档位措辞决定差价**：L3 只写「跨模块」会把多文件但验收明确的改动判成 L3、派给与主会话同价的模型；必须写「跨模块取舍」。
4. **Codex 亏在轮询**：子代理再便宜，主代理以 10–30 秒间隔 `wait_agent` 轮询也会把账吃掉。Codex 自带提示词已写「prefer
   longer waits (minutes)」但未被遵守；`config.toml` 有 `multi_agent_v2.{min,max,default}_wait_timeout_ms` 可配置，默认值
   未能从二进制字符串中读出。spec-guard 与 tier-routing 都加上「一次长等待」指引，补跑 W 组验证。

## 补跑：新门槛（Claude S 组）与一次长等待（Codex W 组）

金额按 tier-guard 口径独立计算（Claude 用 `prices-tierguard.json`；Codex 用 sol $2/$10、luna $0.10/$0.50、缓存命中按输入价 10%）。
与成本报告相比，子代理部分一直完全一致；主会话部分本文系统性偏高（Claude 约 2–3%、Codex 约 8%）。**已与 spec-guard 会话核清**：
价格口径相同，差异来自统计范围——成本报告按 task 时间窗（上一次勾选, 本次勾选] 计，最后一次勾选之后主代理的收尾总结那一轮
不属于任何 task，未计入；本文按整条线程计。对方用 rollout 按整条线程重算，X-N1 / X-N2 得 $0.745 / $0.781，与本文一致。
**合并口径：每次运行的总账用整条线程（本文），每个 task 的明细用成本报告**；成本报告将补一行「未归入任何 task 的用量」。

**Codex W 组**（F 组规则 + 「派出后用 `wait_agent` 一次等到完成，timeout 取最大值」）：

| 运行 | wait_agent | timeout_ms | 每次实际等待（秒） | exec | 子线程 | 合计 |
|---|---|---|---|---|---|---|
| N1 / N2 | 0 | — | — | 23 / 22 | 0 | $0.745 / $0.781（均值 $0.76） |
| F1 / F2 | 25 / 31 | 10000–40000 | 5–40 | 37 / 36 | 5 / 5 | $1.654 / $1.848（均值 $1.75） |
| **W3** | **7** | 3600000 | 53, 86, 118, 132, 148, 54, 119 | 22 | 6 | **$0.835** |
| **W4** | **5** | 3600000 | 57, 85, 152, 261, 89 | 21 | 5 | **$0.706** |

- **超时没有被截断**：每次都等到子代理完成才返回（最长 261 秒）；`timeout_ms` 取最大值可行。
- **轮询消失**：wait_agent 降到约每个子代理一次，exec 回到 N 组水平。W 均值 $0.77，与 N 的 $0.76 **持平**（W4 低于两次 N），
  比 F 便宜一半以上。子线程全部 `gpt-6-luna/high`，tier-guard spawn 记录 6 / 5 条与子线程数一致；W3 的 6 个子线程中 Task 4
  派了 2 次（重派 1 次），其余 task 各 1 次。
- 含义：在 Codex 上，**Luna 子代理 + 一次长等待可以做到「每个 task 都派也不亏」**；要真正省钱，仍需 Task 4 那类能大幅减少
  主会话轮次的 task。

**Claude S 组**（「默认不派」，门槛改为「只派预计改动 3 个以上文件、验收明确的 task」）：

| 运行 | 派活 | 主代理 | 子代理 | 合计 |
|---|---|---|---|---|
| N1 / N2 | 0 | $2.017 / $2.132 | — | 均值 $2.07 |
| S3 | 1（只有 Task 4，L2→sonnet） | $1.840 | $0.672 | **$2.512（+21%）** |
| S4 | 0 | $2.007 | — | $2.007 |

- 新门槛只在一半运行里选中了 Task 4；选中的那次反而更贵——S3 的 Task 4 子代理花了 $0.67，高于 G 组同一 task 的整项成本
  （$0.45–0.63）。**单个 task 的成本波动大于派与不派的差价**，在 Claude 上还不能得出「派 Task 4 这类 task 就省钱」的结论。
- tier-guard 核对：S3 一次派活，transcript、日志、子代理 transcript 三方一致（`upstream_tier=accepted/L2`，实际
  `claude-sonnet-5-5`）；S4 无派活、无日志。

## 最终结论

1. **Codex：可以开派活。** 子代理模型便宜 20 倍（Luna），前提是主代理一次长等待、不轮询；这样即使每个 task 都派也与不派
   持平，遇到能大幅减少主会话轮次的 task 才会省钱。tier-routing 与 spec-guard 规则都已写入「一次长等待」。
2. **Claude：暂不建议开派活。** opus 与 sonnet 的缓存读同价，差价只在新输入与输出；只有极少数能让主会话少跑很多轮的 task
   可能省钱（G 组 Task 4 -23%），但同一 task 的成本波动足以吞掉这点差价（S3 +21%）。
3. **「默认不派」的门槛仍不可靠**：两版门槛下主代理都很少选中合适的 task。规则文字难以稳定地引导主代理判断「哪个 task 值得派」。
4. **档位措辞决定差价**：L3 必须是「跨模块取舍」，否则多文件、验收明确的改动会被派给与主会话同价的模型。
